# Configurator: URL Rewrites Component

## Purpose

Creates and updates URL rewrite/redirect rules in Magento. Supports both 301 (permanent) and 302 (temporary) redirects.

- **Component alias:** `rewrites`
- **File format:** CSV
- **Dependencies:** Store views must exist (referenced by `storeId`).

## CSV Schema

The file must have a header row with these exact column names:

```
requestPath,targetPath,redirectType,storeId,description
```

| Column | Required | Description |
|--------|----------|-------------|
| `requestPath` | Yes | The URL path to redirect from (without leading slash or domain). This is the unique identifier -- if a rewrite with this request path already exists, it is updated. |
| `targetPath` | Yes | The URL path to redirect to (without leading slash or domain). Can also be a full URL for external redirects. |
| `redirectType` | Yes | `301` for permanent redirect, `302` for temporary redirect. |
| `storeId` | Yes | Numeric store view ID the rewrite applies to. Use `1` for the default store view. |
| `description` | Yes | Human-readable description of the rewrite rule. |

## Complete Example

```csv
requestPath,targetPath,redirectType,storeId,description
old-category,new-category,301,1,Permanent redirect for renamed category
promo-summer,summer-sale.html,302,1,Temporary summer promo redirect
legacy-page.html,new-page.html,301,1,Legacy page moved permanently
```

## Instructions for Claude

### Creating a new rewrites CSV file

1. Create a `.csv` file (e.g., `configurator/rewrites.csv`).
2. The first row must be the header: `requestPath,targetPath,redirectType,storeId,description`.
3. Add one row per rewrite rule.
4. Do not include leading slashes in paths (use `old-page` not `/old-page`).
5. Use the numeric store view ID, not the store code.

### Amending an existing file

1. Read the existing file first.
2. To add new rewrites, append rows to the CSV.
3. To update an existing rewrite, find the row with the matching `requestPath` and change the other fields. The component matches on `requestPath` to determine create vs. update.

### Registering in master.yaml

```yaml
rewrites:
  enabled: 1
  method: code
  sources:
    - ../configurator/rewrites.csv
```

## Processing Behavior

- The header row is parsed to determine column mapping, then removed from the data set.
- Each subsequent row is processed as a rewrite rule.
- If a rewrite with the same `requestPath` already exists, it is updated with the new values.
- If no matching `requestPath` exists, a new rewrite is created.
- Rewrites are set as non-autogenerated (`is_autogenerated = 0`).

## Common Mistakes

1. **Missing header row.** The first row must contain the column names exactly as specified. Without it, the component cannot map columns to fields.
2. **Leading slashes in paths.** Do not prefix paths with `/`. Use `old-page` not `/old-page`.
3. **Using store code instead of store ID.** The `storeId` column expects a numeric ID (e.g., `1`), not a store view code (e.g., `default`).
4. **Wrong column order.** The header row defines the column mapping, so the order of columns in the header must match the order of values in each data row.
5. **Confusing 301 and 302.** Use `301` for permanent redirects (SEO-preserving, browsers cache aggressively) and `302` for temporary redirects (no SEO transfer, browsers do not cache).
6. **Duplicate requestPath values.** Each `requestPath` should appear only once in the CSV. If duplicated, the last row processed wins.
